설정은 그대로였다. 그런데 십수 개 서비스를 한꺼번에 배포한 날, 운영 중이던 서비스 전체가 504를 뱉기 시작했다. 처음엔 네트워크나 보안그룹을 의심했다. 다 정상이었다. 문제는 훨씬 안쪽에 있었다.

이후 몇 주에 걸쳐 겉보기엔 서로 다른 장애 세 건을 더 겪었다. 원인을 하나씩 파고들 때마다 결국 같은 자리로 돌아왔다 — "JVM 컨테이너의 메모리 사용률은 실제 부하와 비례한다"는 가정. **이 가정이 틀렸다는 게 세 장애의 공통 원인이었다.**

## 이 글에서 확인한 범위

당시 확인한 운영 신호는 ECS container instance의 agent 연결 상태, 서비스 이벤트, ALB 헬스체크, 태스크 수와 배치 상태였다. 이 신호와 설정을 바탕으로 스케일링 지표와 태스크 배치 전략을 조정했다. 반면 호스트에 직접 접속해 커널 로그를 확인할 수 없었으므로 OOM Killer 개입은 확정하지 않고, 관측된 상태를 설명하는 가설로만 다룬다. 애플리케이션 코드나 JVM 옵션을 직접 바꾼 사례도 아니다.

## 1. 평범한 배포가 전면 장애가 되기까지

평소엔 서비스를 한꺼번에 배포할 일이 없다. 그런데 예외적으로 여러 서비스가 한꺼번에 새 태스크로 교체되는 상황들이 있다. ECS 서비스 설정을 일괄 변경하면서 관련 서비스 전체가 같이 재배포되는 경우, 또는 업무 시간 외에는 서비스를 내렸다가 업무 시작 시간에 다시 띄우는 예약 기반 자동 기동/중지가 그렇다. 배포마다 새 태스크 정의로 컨테이너를 새로 띄우는데, 이게 십수 개 서비스에서 동시에 벌어지니 짧은 시간에 컨테이너가 한꺼번에 기동했다.

문제는 이 컨테이너들이 JVM(Spring Boot) 애플리케이션이었다는 것. 기동 시점에 메모리 사용량이 순간적으로 치솟았고, 여러 태스크가 같은 호스트에 몰리면서 호스트 자체의 물리 메모리가 고갈됐다. 직접 셸로 들어가 dmesg를 확인하지는 못했지만, 정황상 커널 OOM Killer가 개입해 프로세스를 강제 종료시켰을 가능성이 크다. 여기 걸린 게 ECS agent만이 아니었다. SSM agent도 같이 죽었다. 그래서 콘솔에서 인스턴스에 Session Manager로 접속하려 해도 연결이 안 됐다 — 디버깅을 하려고 들어가려는 순간 들어갈 방법 자체가 사라졌다.

agent가 죽은 인스턴스는 `agentConnected=False` 상태가 된다. ECS 스케줄러 입장에선 이 인스턴스가 없는 것과 같다. 그런데 Capacity Provider는 "태스크를 배치할 곳이 없다"는 신호를 "용량이 부족하다"로 해석해 추가 스케일아웃을 시켰다. 새 인스턴스가 뜨고, 거기에도 컨테이너가 몰리고, 같은 이유로 또 agent가 죽고 — 이 순환이 반복되며 결국 클러스터 전체가 무너졌다.

원인을 찾으면서 제일 헷갈렸던 건, ALB 헬스체크가 계속 정상이었다는 점이다. 헬스체크는 컨테이너 포트를 직접 찌르기 때문에, ECS agent가 죽어도 컨테이너 프로세스만 떠 있으면 통과된다. "헬스체크 정상 = 복구됨"이 아니라는 걸 이때 배웠다. 다만 이때는 딱 여기까지만 알아냈다. 완전히 해결됐다고 확신하게 된 건 한참 뒤였다.

## 2. 같은 원인이 다른 얼굴로 다시 나타났다

이 장애를 복구하면서 또 하나 알게 된 게 있다. 호스트 메모리 고갈로 agent가 죽은 인스턴스를 ASG가 종료 대상으로 잡으면 어떻게 되는가.

정상적인 종료 흐름은 "Lifecycle Hook 발동 → 태스크 drain → agent가 완료 보고 → 실제 종료"인데, agent가 이미 죽어 있으면 drain 완료를 보고할 주체가 없다. 그러다 보니 인스턴스는 종료도 못 하고 살지도 못한 채 몇 시간씩 멈춰 있었고, 그 사이 용량 계산 지표까지 왜곡됐다. 같은 뿌리(호스트 메모리 고갈)가 어느 타이밍에 걸리느냐에 따라 다른 증상으로 나타난 것뿐이었다.

## 3. 이번엔 반대 방향 문제였다

몇 주 뒤, 이번엔 정반대의 문제를 만났다. 태스크 2개짜리 서비스가 있었는데, 부하는 이미 한참 전부터 줄어든 상태였다. 그런데도 태스크는 계속 2개인 채로 줄지 않았다.

Target Tracking(목표 추적 방식 오토스케일링)의 스케일인 로직은 이렇게 동작한다. "지금 태스크를 하나 줄이면, 남은 태스크가 그 몫까지 떠안게 될 텐데 그래도 목표치를 안 넘는가?"를 먼저 계산해보고, 안 넘을 때만 실제로 줄인다. CPU처럼 부하가 태스크 수만큼 골고루 나뉘는 지표라면 이 계산은 타당하다.

그런데 이 서비스는 메모리 사용률로 스케일링하고 있었다. 태스크 2개 각각의 메모리 사용률은 약 49%였다. 이걸 "1개로 줄었을 때"로 환산하면 두 몫을 합친 값(약 98%)이 되는데, 목표치인 90%를 넘어버린다. 그래서 알고리즘은 "지금 줄이면 목표치를 넘는다"고 판단해 계속 스케일인을 거부한 것이다.

문제는 이 계산의 전제 자체가 JVM에는 안 맞는다는 데 있다. CPU라면 태스크를 줄였을 때 남은 태스크가 실제로 더 많은 요청을 처리하게 되어 사용률이 오른다. 하지만 JVM은 기동하는 순간 컨테이너 메모리 한도 안에서 힙을 최대한 미리 확보해버린다. 태스크가 1개든 2개든, 요청이 많든 적든 메모리 사용률은 거의 같은 값에 머문다. "태스크를 줄이면 남은 태스크의 부하(=메모리 사용률)가 오른다"는 전제 자체가 JVM에서는 성립하지 않는데, 알고리즘은 그걸 모르고 계산만 하고 있었다.

당시엔 감으로만 의심했는데, 나중에 AWS ECS 공식 문서에서 이 현상을 그대로 짚고 있는 걸 확인했다. Java 8 update 191 이후 JVM은 컨테이너에 할당된 메모리 한도를 감지해 힙 크기를 최대한 크게 자동 설정하기 때문에, 요청량이나 동시성이 늘어나도 메모리 사용률은 거의 일정하게 유지된다는 것 — 그래서 AWS도 Java 기반 서버는 메모리가 아니라 CPU(또는 heap 고갈이 잦다면 커넥션 수·요청률) 기준으로 스케일링할 것을 권장한다.[^1]

## 4. CPU로 바꿨는데도 처음 장애가 다시 났다

3번 장애를 겪으며 확인한 사실 — JVM은 힙을 미리 최대로 잡아버려서 메모리 사용률이 실제 부하를 반영하지 못한다 — 은 1번 장애에도 그대로 적용됐다. 그래서 AWS 문서 권장대로 스케일링 지표를 메모리에서 CPU로 바꿨다. 이거면 됐다고 생각했다.

그런데 몇 주 뒤, 똑같은 패턴의 전면 장애가 다시 났다. 지표는 이미 CPU였는데도.

진짜 원인은 스케일링 지표가 아니라 태스크 배치 전략에 있었다. `spread(AZ) + binpack(memory)` 조합은 인스턴스별 메모리 예약량을 최대한 채우는 방향으로 태스크를 몰아넣는다.[^2] 그러니 여러 태스크가 동시에 기동하는 순간, 결국 같은 소수의 호스트에 집중적으로 쌓였다 — 스케일링 지표와 무관하게 벌어지는 일이었다. 배치 전략을 `spread(AZ) + spread(instanceId)`로 바꿔 태스크를 인스턴스 전체에 고르게 흩어지게 했다. 이후 같은 동시 기동 패턴의 전면 장애는 다시 관측하지 못했다. 다만 장애를 의도적으로 재현하는 부하 시험이나 호스트 메모리 여유의 정량 검증까지 하지는 못했으므로, 이 변경만으로 위험이 완전히 사라졌다고 단정할 수는 없다. CPU로 바꾼 조치는 필요하긴 했지만, 1번 장애의 근본 원인은 아니었다.

## 5. 세 장애를 하나로 꿰는 것

전면 장애, Lifecycle Hook 정체, 스케일인 미작동. 겪을 땐 각각 다른 사건처럼 보였다. 그런데 원인을 거슬러 올라가면 하나였다.

> JVM 워크로드에서 메모리 사용률은 실제 부하와 비례하지 않는다.

이 전제가 깨진 채로 메모리를 신호로 썼더니 세 갈래로 문제가 터졌다. binpack(memory) 배치 전략은 태스크가 예약한 메모리를 기준으로 호스트를 채우는데, JVM은 항상 컨테이너 한도에 가깝게 힙을 미리 확보해버리니 이 예약량이 실제 순간 사용량과 무관하게 늘 높게 잡혀 있었다. 그래서 배치 전략이 "아직 여유 있다"고 보고 밀어넣은 호스트에도 실제로는 여유가 없었고, 거기에 동시 기동 스파이크까지 겹치자 호스트가 통째로 고갈됐다. Capacity Provider는 그 결과(agent 사망)를 용량 부족으로 오판해 스케일아웃을 반복했고, Target Tracking은 늘 일정한 메모리 사용률을 붙잡고 스케일인을 계속 거부했다. 셋 다 뿌리는 같았지만 고쳐야 할 지점은 각각 달랐다.

## 6. 조치 뒤에도 남은 위험

`spread(instanceId)`는 동시 기동 태스크가 한 호스트에 몰리는 위험을 낮춘다. 하지만 클러스터 전체의 가용 메모리를 늘리지는 않는다. 그래서 이후에는 다음을 별도로 확인해야 했다.

- 동시 기동 수와 호스트별 실제 메모리 사용량을 함께 보는 대시보드
- container instance agent 연결 상태와 Session Manager 접속 가능 여부를 포함한 복구 판단 기준
- 배포·예약 기동 시 한꺼번에 교체되는 태스크 수와 클러스터 여유 용량
- CPU가 실제 부하와 비례하는지, 아니면 요청률·동시 연결 수가 더 적합한지 확인하는 사전 부하 시험

## 7. 남은 교훈

- JVM 컨테이너는 CPU나 요청수 같은, 부하와 실제로 비례하는 지표로 스케일링한다
- 메모리는 스케일링 신호가 아니라 OOM을 막기 위한 하드 리밋 용도로만 쓴다
- 태스크 배치 전략도 마찬가지다 — binpack(memory)로 몰아넣지 말고 spread(instanceId)로 고르게 흩어지게 한다
- 헬스체크 통과와 실제 복구는 다른 층위의 신호다 — 뭘 확인하고 있는지 항상 되물어야 한다
- 지표 하나를 고쳤다고 증상이 사라졌다고 단정하지 않는다 — 재발하면 다른 원인이 겹쳐 있다는 신호다

장애 세 건을 따로따로 대응하다가, 나중에야 하나의 잘못된 가정이었다는 걸 알았다. 다음엔 증상이 아니라 가정부터 의심하는 습관을 들이려 한다.

> 관련 사례 확인: [HPA가 잘못된 지표를 따른다](/labs/hpa-wrong-signal/)는 메모리 사용률 대신 실제 수요 신호를 비교하는 별도 시나리오다. 이 글의 ECS 장애를 재현한 사례는 아니다.

[^1]: [Amazon ECS - Optimizing Amazon ECS service auto scaling](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/capacity-autoscaling-best-practice.html) — "The Java-based server" 섹션
[^2]: [Amazon ECS - Use strategies to define Amazon ECS task placement](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task-placement-strategies.html) — `binpack`은 사용하지 않는 CPU 또는 메모리가 가장 적게 남도록 태스크를 배치한다.
